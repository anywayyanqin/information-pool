# 信息池 · 前端原型

带投递、分发、流转、双确认闭环能力的信息池演示原型。纯前端实现（原生 HTML/CSS/JS，hash 路由单页应用），无后端、无真实企业微信对接，数据全部 Mock 并保存在 localStorage。

## 如何打开

- 方式一（推荐）：项目已挂本地服务，浏览器访问 `http://localhost:8123/flow/`
- 方式二：直接双击 `flow/index.html` 用浏览器打开（file:// 协议下同样可运行）

## 术语约定（必须严格遵守）

- **投递**：新建消息时选择入口。只允许投递到「公司总池」或「任意分管池」。
- **分发**：公司总池 → 池树任意层级（分管池 / 部门池 / 小组池）。只有投入公司总池的消息才需要分发；任一总池分发人均可直接分发（无认领环节）。弹窗按池树展示，可展开折叠、按池名/人员搜索、多选，确认后一次性分发。
- **流转**：分管池 → 本线部门池或小组池（可跨级）；部门池 → 本部门小组池。弹窗内按池名/人员搜索、多选。
- **落实人**：消息最终处理完成的那个池的当前处理人。只做分发/流转的池不算落实人。
- **全局编号**：一条消息全程只有一个编号，不管经过多少个池。

## 如何切换身份

页面右上角「当前身份」下拉框，可切换任意 Mock 用户，切换后按钮、可见数据、消息详情内容随权限实时变化。推荐演示身份：

| 身份 | 角色 | 能做什么 |
| --- | --- | --- |
| 张三 | 普通员工（提出人） | 我要填报、看全局汇总时间线、打「提出人确认」（看不到客户信息标签） |
| 王冀湘 | 分管池负责人 | 看研究所线全部消息，回复、流转到本线部门池 |
| 李倩影 | 总池分发人 | 工作台默认「分发」视图，列表/详情内按池树分发到任意层级目标池；可见池管理 |
| 陈立 | 部门池人员 | 在宏观研究部池回复（评论流），或继续流转到本部门小组池 |

身份下拉只保留以上 4 个角色，默认为「普通员工」。

右上角另有「重置 Mock 数据」按钮，一键清空 localStorage 并恢复种子数据。

## 完整流程演示脚本

1. **张三** → 我要填报 → 选信息来源（选「客户反馈」必须选客户名称；选「其他」必须填来源说明）→ 目标池选「公司总池」→ 提交，生成全局编号 M-000x
2. **李倩影** → 工作台默认即「分发」区（仅投向公司总池的待分发消息；「待处理」区是回到她本人的消息，两区数据独立）→ 消息行点「分发」→ 弹窗按整棵池树展开折叠、搜索（池名/人员）、多选（分管池/部门池/小组池均可）→ 确定
3. **王冀湘** → 打开消息 → 回复框输入内容 → 点「提交」→ 选「流转」→ 弹窗搜索、多选本线部门池或小组池 → 确定
4. **陈立** → 部门池回复（评论流，可多次回复、可点赞，所有参与方可见）→「提交」→ 选「流转」到本部门小组池，或选「结束处理」
5. 「结束处理」= 提交回复 + 本池标记已解决；所有最终池都结束后消息进入「待确认」
6. **张三** → 消息详情 → 「提出人确认」打「已解决」→ 消息自动「已关闭」
7. 任一落实人或提出人打「未解决」→ 消息「重新打开」，处理后可再次确认
8. 详情页顶部有「返回上一页」按钮，回到进入详情前的界面

直投场景：新建消息目标池直接选某个分管池，不经过公司总池，由该分管池负责人流转到对应部门池。

## 核心流程

```
投递 ──公司总池──▶ 待总池分发 ──▶ 任一总池分发人按池树分发到一个或多个目标池（分管/部门/小组池均可）
 │                                        │
 │直投分管池                     分管池处理：直接办结，或流转到一个或多个部门池
 │                                        │
 ▼                                        ▼
待分管池处理 ──流转──▶ 待部门处理 ──流转──▶ 待小组处理
                                                    │
                  最终处理池落实人打「落实人确认」（已解决/未解决）
                                                    │
        所有最终落实人「已解决」──▶ 待确认 ──提出人「已解决」──▶ 已关闭
                          任一落实人或提出人「未解决」──▶ 重新打开
```

## 状态机

总消息状态：待总池分发 / 待分管池处理 / 待部门处理 / 待小组处理 / 待确认 / 已关闭 / 重新打开 / 已取消。

分池处理状态：待接收 / 处理中 / 已回复 / 已解决 / 被驳回 / 已流转。

确认状态（落实人、提出人各自独立）：未确认 / 已解决 / 未解决。

关闭条件：所有最终落实人均「已解决」且提出人「已解决」；任一「未解决」即重新打开。

## 可见性规则

- 所有参与方可见该消息的全部回复（评论流：一级评论按时间正序，每条评论可点赞/继续评论，嵌套评论紧跟父评论并缩进，层级不限）
- 客户信息：融合在消息主卡片内的「客户信息」标签，仅后续池处理人员可见，提出人不可见；点击跳转到独立客户信息页（返回回到详情）
- 提出人确认区在所有评论之后的独立区域（已解决 / 未解决）
- 池管理仅总池分发人可见，池树只展示层级与池名称
- 不同分管线的消息互不可见；分管高管可看本线下所有部门池、小组池
- 提出人、总池分发人、系统管理员可看全局汇总时间线
- 关键操作（创建/分发/流转/回复/确认/关闭）仍写操作日志数据，但详情页不再展示操作日志区域

## Mock 数据模型

User（用户）/ Org（部门）/ Pool（池：公司总池→分管池→部门池→小组池）/ Message（消息：全局编号、标题、信息来源、客户名称、提出人确认等）/ MessagePoolLink（消息-池关联：poolType、parentLinkId、是否最终处理池、落实人确认）/ Reply（评论流回复：poolId 记录所属池，parentReplyId 嵌套父评论（null 为一级），点赞 likeCount / likedByUserIds）/ StatusLog（操作日志，仅数据层保留）/ Notification（企业微信 Mock 通知）/ PoolApplication（池申请）。

客户信息卡：`mock.js → getProfile(客户名称)` 按客户名生成确定性的客户360 Mock（标签、交易信息、价格信息、服务跟进记录、历史需求），与 preview.html / 小程序端同一套逻辑。

## 扩展点（正式接入位置）

- `store.js → sendWeComNotification()`：替换为企业微信应用消息 API
- `mock.js → USERS / ORGS`：替换为企业微信通讯录 / 组织架构 API
- `mock.js → CUSTOMERS / getProfile()`：替换为客户工商信息 / 客户主数据接口
- `store.js → loadState / saveState` 及各动作函数：替换为后端 REST 接口
- `perm.js → curUser()`：替换为企业微信 OAuth 登录态与后端鉴权
